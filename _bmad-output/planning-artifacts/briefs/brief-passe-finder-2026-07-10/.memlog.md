- (event) Deux tentatives precedentes (stacks differentes) : ~50 comptes connectes parmi ses propres eleves, utile pour eux, mais jamais adopte formellement par une ecole de danse ; charge de maintenance solo intenable sur 2 stacks.
- (decision) Reconstruction complete hors du vieux code Yii/PHP5, dans un nouveau projet (passe-finder-v2), technos modernes + AWS.
- (decision) Produit a deux faces : danseurs (retrouver/apprendre des passes, proposer un nom alternatif pour une passe deja connue sous un autre nom, retrouver l'enchainement d'un cours precis, trouver des ecoles proches, echanger avec profs/eleves de son cours) et ecoles (visibilite, partage d'enchainements/videos, communication de cours en remplacement de WhatsApp).
- (decision) Donnees existantes (passe-finder-saveDB.gz, ancien projet) a recuperer/migrer plutot que ressaisir a la main.
- (decision) Plateforme cible v1 : web responsive, pas d'app native dans un premier temps.
- (decision) Niveau technique : Alain est debutant/intermediaire sur AWS/stack moderne, veut apprendre - Claude doit expliquer les choix techniques, pas juste les faire.
- (event) Frustration non resolue des tentatives precedentes : visualiser les passes/positions sous plusieurs angles en 3D temps reel (tentative VRML/Blender avec des dummies dansants) - jamais aboutie.
- (decision) Premier jalon vise : refaire le systeme de listes de positions et de passes, livre jusqu'en production avec CI/CD ; features additionnelles (ecoles, communication, 3D) ajoutees iterativement ensuite.
- (decision) Mode de travail choisi : coaching (section par section, prendre le temps de bien penser le projet).
- (decision) Differenciateur cle vs DanceLib (concurrent le plus proche) : DanceLib n'a pas de modele generique Position + Passe (une passe relie une position de depart a une position d'arrivee) permettant de construire facilement des Enchainements a partir de ces briques.
- (event) Workflow qui marchait avant et faisait la valeur du site : pouvoir publier en ~5 minutes l'enchainement travaille en cours du soir, pour que les eleves puissent reviser ensuite.
- (decision) Cadrage de succes v1 tranche : Alain + ses eleves l'utilisent reellement pour leurs cours = succes. L'adoption par des ecoles tierces (que Alain ne controle pas) est une ambition future, PAS une condition du v1. Architecture doit rester ouverte a plusieurs ecoles/profs plus tard, mais rien n'est optimise pour convaincre un tiers inconnu tout de suite.
- (decision) Config BMAD mise a jour : communication_language et document_output_language = French (au lieu du defaut English de l'installeur), coherent avec le contexte francophone du produit.
- (decision) Section Le Probleme validee : priorite = catalogue de passes/positions + creation/partage facile d'enchainements, PAS la mecanique d'adoption par les ecoles. Angle confirme : Alain a perdu son propre outil de travail, ce n'est pas un probleme de vente.
- (decision) Roles v1 : seul Alain (admin) cree/modifie les Positions et Passes du catalogue. Visiteurs = lecture seule. Utilisateurs connectes = peuvent personnaliser (ex: nom alternatif) les positions/passes existantes. Chaque utilisateur peut creer des Enchainements lies a son profil et choisir de les partager ou non.
- (decision) Hors v1 (futur) : les utilisateurs pourront proposer de nouvelles positions/passes, mais soumises a validation par l'admin (Alain) avant publication au catalogue.
- (decision) Section Ce qui differencie validee : moat = modele generique Position/Passe/Enchainement + connaissance metier d'Alain, pas un moat technique fabrique. Le nommage alternatif (meme passe, noms differents selon l'ecole) est garde pour les sections Scope/Vision, pas mentionne comme differenciateur central ici.
- (decision) Section Qui ca sert redigee : Alain (prof/admin), ses eleves (utilisateurs connectes), visiteurs non connectes (lecture seule du catalogue public). En attente de validation utilisateur.
- (decision) Criteres de succes (input utilisateur) : (1) Alain retrouve facilement ses passes/positions/enchainements deja crees (ex: un enchainement sur une musique qu'il a oublie) et peut facilement enregistrer/creer des enchainements pour cours passes et a venir. (2) Stats de visite du site (eleves et externes) comme signal de retour des eleves. (3) Jalon technique reussi = passes/positions migrees vers le nouveau site + CI/CD automatisee (commit -> livraison sans gestes techniques manuels) + moteur de creation d'enchainement fonctionnel avec sauvegarde.
- (decision) Section Scope redigee (dans v1: catalogue admin-only, migration donnees, comptes utilisateurs, personnalisation, moteur enchainements avec sauvegarde/partage, web responsive, stats visite, AWS+CI/CD ; hors v1: multi-ecoles, communication/messagerie, proposition passes par users, 3D, synonymes communautaires, app mobile). En attente de validation utilisateur.
- (decision) Scope ajuste : personnalisation des noms de passe/position (nom alternatif par utilisateur connecte) deplacee hors v1, passee en 'plus tard'. Coherence appliquee dans Solution, Qui ca sert et Scope.
- (decision) Stats de visite v1 : solution simple type Google Analytics/Plausible suffit, pas de dashboard dedie. Premier KPI = nombre de visiteurs par jour.
- (decision) Reframe important sur la vision visualisation : la 3D n'est PAS le but, c'est un moyen parmi d'autres. Le vrai but = aider les gens a comprendre une passe/position. Precedent concret deja fait dans l'ancienne version : lien YouTube attache a un enchainement + recherche des enchainements contenant une passe donnee -> permettait theoriquement de trouver toutes les videos (de personnes differentes) contenant une passe pour la comprendre par recoupement, avec possible chapitrage/timestamp par passe dans une video plus longue. Choix de l'epoque : YouTube plutot que stockage video propre, pour ne pas devenir un hebergeur de video - Alain considere ce choix encore debattable.
- (decision) Section Vision redigee avec le reframe video/comprehension plutot que 3D pour but en soi. En attente de validation utilisateur avant de passer au Resume Executif final.
- (decision) Resume Executif redige, toutes les sections du brief.md sont maintenant remplies. En attente de relecture finale utilisateur avant finalisation (audit memlog, polish editorial, statut final).
