- (version) Recherche web 2026: Aurora Serverless v2 supporte scale-to-zero (min 0 ACU, pause apres >=5min inactivite, ~0 compute en pause, storage 0.10 USD/GB-mois, reveil ~15s). RDS micro ~19 USD/mois (hors budget). Lightsail ~3.5 GBP/mois. DynamoDB ~gratuit mais NoSQL (mauvais fit relationnel). SST v3/Ion fonctionne mais dev ralenti (risque long terme).
- (direction) Risque #1 du projet = CM-1 complexite de maintenance (cause d'abandon des v1/v2), PAS le choix de techno. L'architecture doit biaiser fort vers la simplicite/maintenabilite solo, quitte a payer quelques euros de plus. 'Apprendre AWS' ne doit pas justifier un empilement de services serverless ingerable seul.
- (decision) AD paradigme: MONOLITHE full-stack (une seule base de code: pages+donnees+logique), une seule base relationnelle, deploye en un bloc unique sur AWS. Binds: tous les modules. Prevents: la derive vers un empilement de services serverless ingerables solo (risque CM-1). Choix simplicite/maintenabilite > cout marginal > apprentissage d'un systeme distribue.
- (decision) AD stack: Monolithe Next.js (16.x, React 19, Node 22 LTS) + Payload CMS v3 embarque (admin monte a /admin dans la meme app Next, pas de serveur/CORS/conteneur separe). Langage unique TS. Payload fournit back-office+auth+API generes depuis le schema (equivalent admin Django en TS). Binds: front, back, admin, acces donnees. Prevents: split multi-codebase/multi-langage (SPA+API) et l'admin fait-main.
- (constraint) Contraintes retenues d'Alain: (1) lancement local facile (next dev) obligatoire; (2) tests E2E via Playwright; (3) PHP ecarte; competences: TS/JS > Python. Next.js auto-hebergeable en 1 conteneur Docker ~184Mo Node20+. Payload: exiger @payloadcms/drizzle >= 3.73.0 (fix injection SQL).
- (decision) AD base+hosting: SQLite (libSQL via adaptateur Drizzle de Payload) sur UNE instance Lightsail toujours allumee faisant tourner le conteneur Next+Payload; disque persistant; sauvegarde par streaming continu vers S3 (Litestream ou equivalent libSQL). Cout ~55-60 EUR/an fixe et previsible. Binds: persistance, backup, forme de deploiement. Prevents: DB managee/serverless (cold start, complexite) et perte de donnees (backup continu obligatoire).
- (decision) AD auth: authentification integree de Payload (collection users, email/mot de passe, sessions) — PAS de service AWS Cognito ni d'auth maison. Resout la question ouverte Q-1 du PRD. Binds: comptes, roles, permissions. Prevents: un systeme d'auth externe supplementaire a gerer.
- (decision) AD modele de donnees (collections Payload): Danse{nom}, Position{nom,description,image,danse}, Passe{nom,description,positionDebut,positionFin,difficulte?}, Enchainement{titre,description,notes,date,auteur,visibilite prive|partage,youtubeUrl?,passesOrdonnees[]}, User(auth Payload + flag admin), Favori{user,enchainement}. danse RETIREE de Passe: derivee de ses positions. Champs archives caches: youtubeUrlLegacy, customName, PersonnalizePasse.
- (decision) AD invariants domaine: (1) ecritures TOUJOURS via Payload (acces/validation/hooks), lectures possibles en Drizzle direct; (2) aretes du graphe sur Passe (positionDebut/Fin), moteur de compo = lecture serveur; (3) admin possede Danse/Position/Passe, auteur possede son Enchainement; (4) visibilite: partage=lisible public sans login, prive=auteur; reverse-lookups & favoris ne remontent que le partage; (5) meme-danse: positionDebut.danse==positionFin.danse, danse de la passe deduite; (6) suppression bloquee si reference; (7) favori seulement sur enchainement partage d'autrui; (8) champs archives non exposes v1.
- (decision) AD images: uploads (images de positions) stockes dans S3 via l'adaptateur de stockage officiel de Payload; decouple de l'instance, survit aux redeploiements. Meme S3 que la sauvegarde DB. Placeholder no_position pour position sans image (FR-2).
- (decision) UI danse masquee en v1: champ danse sur Position (defaut rock 6 temps) mais aucun selecteur de danse dans admin/UI v1. Modele garde la dimension (PRD FR-6), UI l'ignore.
- (assumption) REMONTEE PRD: ajouter un champ 'nom' sur Position et Passe (implique par les parcours: 'position fermee', 'nom des passes' vu par Lea) — le PRD ne le listait pas explicitement. A reconcilier avec le PRD a la finalisation.
- (decision) AD deploiement/CICD: app tourne sur une instance Lightsail (VM+Docker) car SQLite exige un disque persistant (pas de service conteneur ephemere). Conteneur Next+Payload monte le volume SQLite + side-car backup->S3. Pipeline: push main -> GitHub Actions build image Docker -> ghcr.io (gratuit) -> deploy sur l'instance (pull+restart). Realise FR-41 commit->prod sans geste manuel. Binds: build, release, persistance.
- (decision) AD environnements: local (next dev, SQLite fichier local, uploads dev) lancable en une commande; prod (instance Lightsail). PAS de staging separe en v1 (simplicite); filet de securite = tests Playwright en local + dans la CI avant deploiement.
- (decision) AD migration (F5): script one-off lit passe-finder-saveDB.gz et peuple via l'API Local de Payload dans l'ordre Danses->Positions->Passes->Enchainements; tous enchainements->Alain; youtube_url/customName archives non exposes; images manquantes->no_position; verifiable (comptage source vs cible) et rejouable. Teste en local avant prod.
- (decision) AD analytics (Q-3/FR-43): Cloudflare Web Analytics (gratuit, leger, sans banniere cookies, console externe) pour visiteurs/jour. Distinction connectes vs anonymes derivee cote app (l'app connait l'etat de session), pas via l'outil de stats. Pas de tableau de bord in-app en v1.
- (version) Verifie: Payload supporte Next.js 16 depuis v3.73.0 (2026-01-23), exige Next >= 16.2.2. 3.73.0 corrige aussi l'injection SQL. Stack Next16+Payload3.73 confirme coherent. Pin Next ajuste a >=16.2.2.
